# Lazy and file inputs for `profile()` — design, sampling, memory

## What changed

`onceover.profile` accepts, in addition to a Polars DataFrame:

- a Polars `LazyFrame`;
- a path (`str` or `os.PathLike`) to a Parquet (`.parquet`, `.pq`),
  CSV (`.csv`), or IPC (`.ipc`, `.feather`, `.arrow`) file, read with
  the matching `pl.scan_*` constructor.

New keyword-only parameters on `profile()`:

- `source_row_cap` (default 200,000): the most rows materialized from
  a lazy or file source. Sources at or under the cap are collected in
  full.
- `exact` (default `False`): collect the whole source regardless of
  the cap. This is the opt-in for exact statistics on
  larger-than-memory inputs; memory is then the caller's
  responsibility.
- `sample_seed` (default 0): seed for the source sample.

Every report produced from a lazy or file input carries a top-level
`source` block (absent — not null — for DataFrame inputs, so existing
reports are unchanged):

```json
"source": {
  "kind": "parquet",
  "rows": 5800000,
  "rows_profiled": 200000,
  "basis": "sampled",
  "sample": {"method": "stratified", "seed": 0, "cap": 200000}
}
```

`basis` is `full` when the whole source was collected (the `sample`
object is then absent). Coverage gains an `input` entry in the same
terms, and when the basis is sampled every finding's evidence scope
records `sampling: "sample"` with `population_rows` set to the source
row count — sampled numbers are never presented as population
numbers. The overview headline and the digest carry the same
statement. Column cards describe the profiled frame; the `source`
block states which frame that was.

The report schema version is unchanged: the block is additive and
absent for the existing input, and the corpus identity check below
verifies every pre-existing report is byte-identical.

## Sampling design

When a source has more rows than the cap, the sample is drawn at the
source, before any profiling: one row per equal stratum of the
source (stratum `j` covers source rows
`[floor(j*N/cap), floor((j+1)*N/cap))`), the row within a stratum
chosen by a splitmix64 hash of the stratum index and the seed. This
is the same stratified design the relationship searches already use
(`onceover_core::sample_rows`), with no periodic stride to alias
against periodic data. The lazy plan is a row-index filter, collected
with the streaming engine, so source memory stays bounded by the
sample, not by the source. Sampling is deterministic: the same
source, cap, and seed give the same sample and the same report.

Exact row counts come from the source itself: Parquet footers carry
them, and for other sources a `len()` aggregation over the lazy plan
answers without materializing columns.

## Memory budget (declared before measuring)

Declared budget: **peak RSS of the profiling process ≤ 2 GiB** when
profiling the fixture below at the default cap. Peak RSS is the
child process's `ru_maxrss` from `wait4` — the same quantity
`/usr/bin/time -v` reports as Maximum resident set size — measured
around a fresh interpreter running only the fixture profile.

## Fixture

Generated by a script (kept with the benchmark harness, not
committed): 5,800,000 rows × 220 columns, 10,869,647,750 bytes
(10.12 GiB) on disk, compression off, 200,000-row row groups, seed
20261104. Planted structure past column 64:

- `col_100 = 2.0 * col_099 + 1.0` — exact affine identity;
- `col_150` (40 codes) determines `col_151` (its label) — exact
  functional dependency;
- `col_180 = 0.8 * col_179 + 0.6 * noise` — numeric association,
  population correlation 0.8.

## Results

Profiling the fixture by path at the default cap (200,000 rows,
seed 0) reported exactly the source block shown above: kind
`parquet`, 5,800,000 source rows, 200,000 rows profiled, basis
`sampled`. Profile wall time was 435 s on the benchmark machine
(a shared 4-core VM under load; the sample collect alone scans the
full 10.12 GiB).

**Peak RSS: 1,544,440 KiB (1.47 GiB) — within the declared 2 GiB
budget.**

All three planted relationships were recovered from the sample:

- the affine identity, as a selected `functional` finding:
  "col_100 = 2.000000·col_099 + 1.000000 within tolerance on all
  200000 non-missing row pairs" (the arithmetic-identities pass
  also reports 1 identity among 2 candidate pairs);
- the functional dependency, in the grouped findings as exact
  `functional` findings in both directions ("col_150 → col_151
  (col_151 is a function of col_150; 0 violations in 200000
  rows)"), and in the selected findings as a `duplicate_encoding`
  finding: "col_150 and col_151 encode the same grouping: 40
  levels, paired one-to-one";
- the numeric association, as `predictive` findings in both
  directions (col_179 predictable from a set including col_180,
  and conversely).

The report held 26 selected findings and 2 grouped findings.
Every evidence block in both lists carried scope
`sampling: "sample"` with `population_rows: 5800000` — no sampled
number is presented as a population number.

Report selection is where the recovery needs care when reading:
the report caps how many findings are selected, and the grouped
statements sit under `grouped_findings`. A checker that looks only
at the selected findings, and only for exact finding-type names,
will miss the functional dependency even though the profile found
it.

## Corpus identity (DataFrame path unchanged)

Full-report dumps over the runnable corpus — 23 of the 34
registered datasets profile; the other 11 have no local data file
and are skipped by the corpus runner — were produced with the
pre-change build and with this change, both against the same
corpus files. A recursive diff dropping only `elapsed_ms` reports
**23 of 23 identical**: the DataFrame path's reports are unchanged
by this work.
